# 수정 웨이브 지시

## A. 기능 계층 수정 (UI 작업 중 보류한 domain·data 항목)

목표: `<로그 경로>`의 "기능 계층 보류" 항목 <번호 목록>을 고친다. 기준은 `prd.md` 결정, `design_spec.md`, 사용자 결정 `<U-ID>`.

규칙
1. 맡은 모듈의 `lib/features/<module>/{domain,data,presentation}/`만 수정. 공통 파일은 보고.
2. domain은 순수하게, 비즈니스 규칙은 UseCase에.
3. 바꾸지 않을 것: <명시 — 예: 결과 미확정 처리, 재전송 금지>.
4. presentation에 두었던 임시 우회는 domain 수정 후 제거해 판정 지점을 한 곳으로.
5. `flutter test`·빌드 실행 금지, 테스트 파일 수정 금지. `dart analyze lib` + `dart format`(맡은 폴더) 0건.

보고 (8줄 이내): 항목별 바꾼 내용(파일), 화면에 보이는 변화, 깨질 것으로 예상되는 테스트.

## B. 테스트 수정

배경: 전체 실행 결과 통과 <n>, 컴파일 실패 <n>개 파일, 실행 실패 <n>건.

원칙
1. 테스트는 현재 승인된 동작(명세·PRD·사용자 결정)을 검증하도록 고친다. 옛 위젯·옛 키·옛 동작 기대는 새 것으로.
2. **테스트를 코드에 억지로 맞추지 않는다.** 코드가 기준과 다르면 테스트가 아니라 `lib/`를 고치고 "결함 수정"으로 따로 보고. 다른 모듈·공통 파일이면 보고만.
3. 커버리지 게이트 유지. 새 규칙에는 테스트 추가.
4. 기존 테스트의 의도는 유지. 의도 자체가 기준과 반대가 됐을 때만 지우고 이유를 보고. 안전 테스트(재전송 금지·결과 미확정)는 반드시 남긴다.
5. 맡은 테스트 폴더만 수정·실행(`flutter test <폴더>`). 공유 헬퍼는 지정된 담당만 수정.
6. `dart analyze test/<폴더>` 0건.

보고 (10줄 이내): 고친 파일 수, 통과·실패 수, 결함 수정(파일:행, 근거), 다른 담당에게 요청, 의도를 바꾸거나 지운 테스트와 이유.
