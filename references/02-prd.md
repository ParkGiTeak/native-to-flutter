# 2단계 — PRD

목표: "무엇을 만들고, OS 간 다른 동작을 어떻게 하나로 정했는지"를 결정 ID로 고정한다. 구현 지시서·명세·테스트가 모두 이 결정 ID를 근거로 단다.

## 1. 작성 방식

- 작성자: 오케스트레이터(또는 Opus 에이전트 1개)가 본문을 쓴다.
- 리뷰어: Fable 서브에이전트 또는 사용자가 붙인 외부 모델. 리뷰어는 본문을 직접 고치지 않고 로그에 피드백을 남긴다.
- 절차는 `collaboration.md`의 "공동 작성 합의"를 따른다: 본문은 `<!-- PRD-START rN -->`~`<!-- PRD-END rN -->` 블록, 대화는 `logs/prd_log.md`에 추가만. 같은 리비전에 양측이 완료를 선언하면 확정.
- 사용자 결정이 필요한 항목은 합의 중에 모아서 한 번에 묻는다. 정책 승인(PO·서버·법무)이 안 된 항목도 담당·게이트를 적어 두면 문서 합의는 완료할 수 있다.

## 2. PRD 목차

```markdown
# <앱> Flutter 전환 PRD

(상태 표: 참여자 / 역할 / 완료 리비전)

## 1. 개요 — 문제, 목표, 범위(In / Out / 결정 필요), 성공 지표
## 2. 사용자와 핵심 여정 — 가장 중요한 여정 3~5개(예: 가입 → 결제수단 등록 → 핵심 기능 사용)
## 3. 현행 구조 요약 — OS별 구조·의존성 요약(분석서 링크)
## 4. 비즈니스 로직 차이와 결정 (BOTH) / 원본 동작 정정과 새 플랫폼 결정 (단일 OS)
   4.1 P0 / 4.2 P1 / 4.3 P2 — 결정표
   4.4 재현하지 않을 원본 결함
   4.5 결정 요약표 (D01~Dnn, 구현 기준)
## 5. 통합 원칙 — SKILL.md 원칙을 이 앱 기준으로 6~8줄
## 6. API 계약 — API-ID별 요청·응답·성공 판정·오류 매핑·인증 여부, 공통 헤더, 암호화, 페이징 규약
## 7. 화면 명세 — S-ID별 목적, 진입·이탈, 로그인 필요, 상태(로딩·빈·오류), 연결 결정 ID
## 8. 기능 요구사항 — FR-ID별 규칙(푸시 type→화면 표, 문구표 포함)
## 9. 상태 흐름 — 결제·주문처럼 결과가 불확실한 흐름의 상태 기계(요청 중 / 성공 / 거절 / 결과 미확정)
## 10. Flutter 아키텍처 — 레이어, 모듈 목록, 플랫폼 어댑터 목록(OS 차이는 어댑터 안에만)
## 11. 데이터 이관·보안·운영 — 앱 ID·서명·버전, 로컬 데이터 이관표, 보안, 환경, 관측, 최소 OS
## 12. 단계·게이트·일정
## 13. 검증 — 테스트 계층, 인수 시나리오 T-ID
## 14. 결정 기록과 오픈 이슈 — DEC-ID(사용자·서버 승인 필요), 서버 요청 목록
```

## 3. 결정표 형식

```markdown
| ID | 항목 | iOS 현재 | Android 현재 | 결정 | 서버 | 근거 |
|---|---|---|---|---|---|---|
| D01 | 비밀번호 로그인 검증 | 정규식 강제(17자 이상 계정 로그인 불가) | 길이만 검사 | 로그인은 형식 검사 없이 서버가 판정. 가입·변경은 서버 규칙과 동일 | ● | iOS `Login.swift:42`, AOS `LoginVM.kt:88` |
```

결정을 쓸 때 확인할 것:

1. 이 결정으로 **어느 OS 사용자든** 지금 되는 일을 못 하게 되는가? 그렇다면 틀린 결정이다.
2. 서버가 이미 두 방식을 다 받고 있는가? 두 앱이 운영 중이면 받고 있다는 뜻이다. 더 나은 쪽을 고르면 된다.
3. 금액·유효성·재고처럼 서버가 판단할 수 있는 것은 서버 값을 쓴다. 앱 계산은 표시용으로만.
4. 결과가 불확실한 요청(결제·등록·신고)은 자동 재전송하지 않는다. "결과 미확정" 상태와 확인 경로를 정한다.

## 4. 이관표 (기존 앱 업데이트일 때 필수)

```markdown
| 데이터 | iOS 저장 (키) | Android 저장 (파일·키) | 처리 |
| 세션 토큰 | UserDefaults `token` | SharedPreferences `<applicationId>_preferences` / `token` | secure storage로 이동 → 서버 검증, 실패 시 재로그인 |
| 설정 캐시 | … | … | 서버 값으로 덮어씀 |
| 최근 검색 | … | … | 정규화 후 이관 |
| 푸시 토큰 | … | … | 버리고 재발급·재등록 |
```

원칙: 1회 실행·이관 버전 기록, 실패해도 크래시 없이 재로그인, 실패 시 원본을 지우지 않음, 카드번호·비밀번호 원문은 이관하지 않음. Android 기본 SharedPreferences 파일명은 `<applicationId>_preferences`지만 라이브러리·모듈이 다른 파일명을 하드코딩한 경우가 있으니 분석서에서 확인한다. 이관은 네이티브 코드로 원본 저장소를 직접 읽어야 한다(Flutter 저장소 패키지는 원본 키·파일을 못 읽는다 — `05-build.md` 5단계 6항).

## 5. 인수 시나리오

`T-ID / 대상(FR·D) / 입력·상황 / 기대 결과`. 반드시 포함:

- 구버전 앱 → 새 버전 업데이트 후 로그인 유지·데이터 유지
- 계정 A 로그아웃 → 계정 B 로그인 시 A의 캐시가 보이지 않음
- 결과 미확정(타임아웃) 결제·등록에서 재전송이 일어나지 않음
- 푸시: 포그라운드·백그라운드·종료 상태 탭 → 같은 목적지
- 권한 거부·영구 거부·설정에서 허용 후 복귀
- 오프라인 시작, 서버 오류 응답, 토큰 만료
- 암호화가 있다면 원본 암호문과 바이트 단위 일치(테스트 벡터)
- 보안 검사(루팅·탈옥) 차단과 release 로그에 민감정보 없음

## 6. 모드별

- **BOTH**: 4장이 핵심이다. 차이 하나하나에 결정을 단다.
- **단일 OS**: 4장은 "원본 결함 정정"과 "새 플랫폼 결정"(`new_platform_gaps.md` 항목별 결정)으로 바뀐다. 새 OS로 처음 출시한다면 11장에서 이관은 원본 OS에만 적용하고, 새 OS는 새 앱 ID·서명·스토어 등록 절차를 적는다.

## 7. 게이트

PRD 리비전에 양측 완료 선언, P0 결정 전부 확정(서버 확인 대기 항목은 "현행 유지 + 오픈 이슈"로라도 결정), 사용자에게 결정 요약을 보고. 합의 과정에서 쓴 대화 로그는 사용자가 원하면 확정 후 정리(삭제)하고 본문만 남긴다.
