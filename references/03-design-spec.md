# 3단계 — UI 인벤토리·디자인 명세

목표: Flutter가 그려야 할 **목표값**을 화면 단위로 확정한다. 모듈 에이전트가 이 문서만 보고 화면을 만들 수 있어야 한다. 원본 앱과 "똑같아 보이는" 결과는 이 문서의 해상도로 결정된다.

이 단계를 구현 전에 끝낸다. 기능만 먼저 구현하고 UI를 나중에 맞추면, 에셋·폰트·문자열·줄바꿈·전환 방식이 원본과 달라 전 화면을 다시 고치게 된다.

## 1. UI 인벤토리 (OS별, 병렬)

OS마다 에이전트 1개(`templates/analysis_brief.md`를 UI용으로 채워 사용). 산출물 `design/<os>_ui_inventory.md`:

1. **전역 요소**: 색(팔레트·하드코딩 리터럴·알파), 폰트(번들 여부, 패밀리, weight), 텍스트 스타일(크기·행간·자간), 글자 확대 대응(iOS Dynamic Type / Android sp 사용 여부), 간격·모서리·테두리·그림자, 상태바·내비게이션 바, 화면 배경, 앱 아이콘·런치 스크린·스플래시
2. **공용 컴포넌트**: 버튼, 입력칸(밑줄·테두리·포커스 색), 내비 바(뒤로·닫기), 팝업·알럿·액션시트(등장 애니메이션 포함), 토스트, 로딩(모양·dim·취소 가능 여부), 새로고침, 빈 화면, 바텀시트(높이 단계), 피커, 체크박스·라디오·스위치, 리스트 셀, 화면 전환(push·modal·fade), 키보드 처리
3. **에셋**: 이름, 경로, 배율(1x/2x/3x, mdpi~xxxhdpi), 크기, 사용 화면. 벡터/비트맵 구분
4. **문자열**: 리소스 키와 원문(줄바꿈 포함 그대로), 하드코딩 문자열 위치
5. **화면별**: 레이아웃 트리(요소, 기준 객체, offset, 크기), 요소표(텍스트 스타일·색·줄 수·말줄임·에셋·문자열 키), 상태(기본·비활성·선택·로딩·빈·오류), 인터랙션(탭 목적지, 뒤로가기, 키보드, 중복 탭)

근거: iOS는 storyboard/xib XML 좌표, SnapKit·Auto Layout 코드, SwiftUI modifier. Android는 layout XML, dimens/colors/strings/styles, Compose 코드. 라이브러리 기본값(예: 바텀시트 라이브러리의 기본 높이)은 라이브러리 버전 태그의 원본을 근거로 단다.

## 2. 대조와 결정 (BOTH)

1. 두 인벤토리를 대조해 차이 목록을 만든다: `항목 / iOS 값 / Android 값 / 기준 OS 적용 결과 / 예외 여부(a·b·c)`.
2. 기준 OS로 정해지지 않는 것(둘 다 문제, 기준 OS가 기능을 막음, 원본에 없어 새로 정해야 함)은 **결정 후보**로 모아 사용자에게 묻는다. 결정은 `decisions.md`에 `U-번호`로 기록한다.
3. 외부 모델이 같은 원본을 따로 분석하는 경우(사용자가 붙였을 때), 서로의 인벤토리를 대조해 불일치를 `logs/design_log.md`에서 합의한다.

**단일 OS**: 대조 대신 "새 OS 적용 규칙"을 정한다(예: Android 하드웨어 뒤로가기 = 화면의 닫기·뒤로 버튼과 같은 결과, iOS에서 Android식 툴바를 쓸지 여부). 이것도 U-번호 결정 후보다.

자주 결정 후보가 되는 것: 시스템 폰트 vs 번들 폰트, 글자 확대 고정 여부, 오류·재시도 UI(원본에 없으면 신설 여부), 로딩 표시 모양, 팝업 애니메이션, 사이드 메뉴 방식, 모달 닫기 버튼 vs 뒤로가기, OS 네이티브 화면(카메라·OCR) 직접 사용 여부.

## 3. `design_spec.md` 목차

```markdown
# <앱> Flutter UI/UX 명세

## 0. 문서 정보 — 리비전 표, 기준 원칙(기준 OS·예외 3종·기능 규칙 우선·도달 불가 UI 제외), 사용자 결정 U 표, 표기법(근거 약어, 확실성 표시, 레이아웃 트리 문법), 리비전별 변경 요약
## 1. 디자인 토큰 — 색, 타이포(폰트·스타일·행간·글자 배율·글 넘김), 간격, 모서리, 테두리, 그림자, 상태바, 배경
## 2. 공용 컴포넌트 — 컴포넌트별 Flutter 이름, 수치, 상태, 사용 규칙. 오류 표시 규칙(조회 실패 / 제출 실패 / 결과 미확정) 포함
## 3. 에셋 — 가져올 목록(원본 경로 → Flutter 경로, 배율), 앱 아이콘·런치, 제외 목록
## 4. 문자열 — 키 규칙(`s<화면번호>_<이름>`), 공용·화면별 키와 원문
## 5. 화면별 명세 — S-ID마다: 진입, 레이아웃 트리, 요소표, 상태표, 인터랙션표, 연결 결정(D·U·X)
## 6. 플랫폼 예외 목록 — X-ID, 유형(a/b/c), 내용, 대가
## 7. 실기기 확인 목록 — 코드로 확정 못 하는 값(실측 필요), 우선순위
## 부록 — 인벤토리 간 불일치와 채택 근거, 미결 항목(담당: 사용자/실기기/서버/공동)
```

표기 원칙:

- **목표값만** 적는다. OS 비교는 6장 예외에만.
- 단위: iOS pt = Android dp = Flutter logical px.
- 레이아웃 트리 예: `title [h56] ← safeTop + 0, L 0, R 0`.
- 스타일 예: `regular17 · gray1` = 토큰 이름 조합.
- 미결 값은 `[미결 — 담당]`. 미결 값은 합의·사용자 지시 전에는 구현 근거가 아니다.

## 4. 합의와 리비전

- 작성: 오케스트레이터(또는 Opus 에이전트). 화면이 많으면 화면 묶음별로 에이전트를 나눠 5장을 쓰게 하고 1~4장은 한 곳에서 쓴다.
- 리뷰: 리뷰어가 화면별로 원본 인벤토리·원본 코드와 대조. **화면별 승인**을 허용한다(승인된 화면부터 구현 가능). 등록부: `| S-ID | 리뷰어 | 작성자 | 리비전 |`.
- 리비전을 올릴 때 0장에 "rN → rN+1 변경 요약" 표(ID / 변경 / 반영 절)를 추가한다. 구현 뒤 사용자 결정으로 바뀔 때도 같은 방식(8단계 실기기 QA 루프에서 계속 리비전이 올라간다).
- 결정 ID(U·D·X·실기기 항목)를 새로 붙일 때 기존 ID와 겹치지 않는지 grep으로 확인한다.

## 5. 게이트

모든 화면 승인(또는 화면별 승인 + 미승인 화면은 구현 보류), 결정 후보 전부 사용자 결정, 미결 목록에 담당 지정.
