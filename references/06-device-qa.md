# 8단계 — 실기기 QA 루프

목표: 사용자가 실기기에서 원본 앱과 나란히 비교하며 찾은 차이·결함을 빠르게 고치고, 그 결정을 문서에 남긴다. 실제 전환에서 가장 많은 수정이 나오는 단계다.

## 1. 준비

- `qa_device_checklist.md`: 명세 7장 실기기 확인 목록 + PRD 인수 시나리오를 시나리오 표로(`T-ID / 사전조건 / 절차 / 기대 결과 / iOS / Android / 비고`). 빌드·설치 명령과 결과 기록 템플릿 포함.
- 자동화 가능한 시나리오는 `integration_test/`로 실기기 스위트를 만든다. 테스트 계정 등 QA 전용 값은 별도 define 파일(예: `env/qa.json`, 저장소에 올리지 않음)로 주입한다. 자동 스위트가 수동 체크리스트를 대신하지는 않는다(본인인증·결제·카메라·푸시는 사람이 확인).
- 설치: 사용자가 기기를 연결하면 `flutter devices`로 ID를 확인하고 `flutter run`(또는 `--release`) / `flutter install`로 설치. 기기 연결이 끊기는 경우가 잦으니 장시간 대기 명령은 백그라운드로 돌리고 멈추면 끊는다.
- iOS debug 빌드는 디버거가 붙어 있어야만 실행된다. 들고 다니며 볼 빌드는 `--release`/`--profile`로 설치한다고 사용자에게 알린다.
- 같은 앱 ID에서 debug 키 서명 빌드와 release 키 서명 빌드는 서로 덮어쓸 수 없다(Android). 재설치하면 로컬 데이터가 지워진다는 것을 설치 전에 알린다.

## 2. 피드백 한 건 처리 순서

사용자는 보통 번호 목록으로 여러 건을 한 번에 준다("1. … 2. …").

1. **분류**: 결함(명세와 다름) / 원본과 다름(명세가 원본과 다름) / 새 결정(원본과도 다르게 바꾸고 싶음) / 질문.
2. **질문이면** 원본 코드를 근거로 답한다("원래 네이티브는 어떻게 하나"). 추측하지 않는다. 답한 뒤 사용자가 결정을 내리면 3으로.
3. **결정이면** `decisions.md`에 `U-번호`로 기록: `항목 / 결정 / 적용 범위(화면·컴포넌트) / 근거(사용자 말 인용, 날짜)`. "다 너가 추천하는 걸로"도 결정이다 — 추천안 내용을 그대로 기록.
4. **원인 분석**: 재현 경로를 코드로 따라가 원인을 찾는다. 증상만 가리는 수정(예: 버튼에 딜레이)은 하지 않는다. 같은 원인을 가진 다른 화면이 있는지 찾는다.
5. **수정 + 회귀 테스트**: 수정마다 실패하던 시나리오를 테스트로 고정.
6. **검증**: 관련 테스트 → 전체 `flutter test` + `dart analyze`. 사용자 기기에 다시 설치(요청 시).
7. **문서 동기화**(같은 라운드에서): 디자인 명세 리비전 올리고 변경 요약 추가, 해당 화면 절·예외·실기기 목록 수정, PRD에 영향이 있으면 PRD, 구현 로그에 수정 기록, QA 체크리스트 항목 추가.
8. **보고**: 건별로 원인 한 줄, 수정 내용, 검증 결과, 사용자가 기기에서 다시 볼 것.

## 3. 원칙

- 원본에 있던 문구·기능을 뺐던 것이 발견되면 즉시 사용자에게 알리고 복원 여부를 묻는다.
- "원본과 같게"라는 요청은 원본 코드를 다시 열어 값을 가져온다. 이전 인벤토리를 믿지 말고 원본으로 재확인.
- 결정이 이전 결정을 뒤집으면 이전 U 행에 "U-n으로 대체"를 표시한다. 지우지 않는다.
- 사용자가 다른 작업 흐름(다른 세션·사람)으로 코드를 바꿨다고 하면, 변경 파일을 찾아 읽고 명세·결정·로그를 코드에 맞춰 갱신한다. "기록은 중요하다" — 코드와 문서가 다르면 코드가 기준이고 문서를 고친다.

## 4. 종료

사용자가 "완료"라고 하거나 남은 항목이 모두 닫히면 9단계로. QA 체크리스트 결과 열을 채우고, 미결 항목은 담당과 함께 남긴다.
