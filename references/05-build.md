# 5~7단계 — 공통 기반, 모듈 구현, 통합 테스트

## 5단계 — 공통 기반·플랫폼 POC

오케스트레이터가 직접 하거나 계층별 에이전트에 맡긴다. 공통 파일은 이 단계에서 확정해 두어야 6단계 병렬 작업이 충돌하지 않는다.

1. **프로젝트 생성**: `flutter create --org <원본 조직> --project-name <name> --platforms <착수 기록의 대상 플랫폼> <app>_flutter`. 원본이 있는 OS는 번들 ID·applicationId를 **원본과 똑같이** 맞춘다(철자가 이상해도 고치지 않는다 — 고치면 다른 앱이 된다). 새로 지원하는 OS의 앱 ID는 착수 때 사용자가 정한 값(아래 "모드별").
2. **flavor·env**: `lib/main_<flavor>.dart`, Android `productFlavors`, iOS 스킴·빌드 구성·xcconfig, `env/<flavor>.json` + `--dart-define-from-file`. IDE 실행 구성(VS Code `launch.json`, Android Studio `.run/*.run.xml`)을 같이 만들어 커밋한다 — 매번 긴 명령을 치게 하면 사용자가 불편해한다. iOS flavor 함정과 상세는 `07-release.md` 4절.
3. **core**: 네트워크, 에러, MVI 베이스, 저장소, 암호화(+원본 암호문 테스트 벡터), 설정.
4. **디자인 시스템**(명세 1~4장): 토큰, 공용 컴포넌트, 에셋(배율 변형까지 — 1x만 가져오면 고해상도 기기에서 흐리게 나온다), 문자열 키 전체, 글자 배율 정책, 상태바 규칙. 하나의 barrel import로 쓰게 한다.
5. **라우터**: 경로 상수, 페이지·바인딩, 로그인 가드(원래 목적지 복원), 화면별 전환 방식.
6. **플랫폼 어댑터·플러그인**: 원본 네이티브 코드를 MethodChannel로 이식할지 pub 패키지를 쓸지 정한다. 원본 SDK(OCR·결제·본인인증 등)는 로컬 플러그인(`packages/`)으로 감싼다. 원본에 없던 SDK로 바꾸지 않는다(SKILL.md 원칙 6).
   레거시 데이터 이관은 반드시 네이티브 코드(MethodChannel 또는 로컬 플러그인)로 읽는다. Flutter `shared_preferences`는 Android에서 `FlutterSharedPreferences` 파일만, iOS에서 `flutter.` 접두 키만 읽고, `flutter_secure_storage`는 자기 서비스명의 키체인 항목만 읽기 때문에 원본 UserDefaults·Keychain(서비스명·access group)·SharedPreferences 파일을 볼 수 없다.
7. **실기기 POC 게이트**: 사용자에게 기기 연결을 요청해 **대상 플랫폼 전부**에서 어댑터마다 성공·취소·복귀를 확인. 에뮬레이터 통과로 대신하지 않는다.

### 모드별

| 항목 | 원본이 있는 OS | 새로 지원하는 OS (단일 OS 모드) |
|---|---|---|
| 앱 ID | 원본과 동일 | 사용자 결정(원본 OS와 같은 역도메인 이름 추천, 스토어에서 이미 쓰이는지 확인) |
| 레거시 이관 어댑터 | 원본 저장소를 읽는 네이티브 코드 | 이관 대상이 없으므로 no-op 구현(인터페이스는 같게) |
| 플랫폼 공백 | - | `new_platform_gaps.md` 결정대로 구현(뒤로가기, 권한, 알림 채널·권한, 시스템 바) |
| 원본 SDK | 로컬 플러그인으로 감쌈 | SDK가 새 OS를 지원하지 않으면 PRD에서 정한 대체안(사용자 결정) |
| POC | 실기기 | 실기기(이 OS의 첫 실행이므로 권한·푸시·딥링크를 특히) |

## 6단계 — 모듈별 구현

### 순서와 단위

- impl_plan의 Phase·모듈 순서를 따른다. 핵심 여정 모듈부터.
- 기본 방식(기능 구현): **모듈 1개씩**, 모듈 안에서 계층별 에이전트(data, domain, presentation, test)를 둔다. 계층 간 의존이 있으니 data+domain → presentation → test 순.
- 명세가 확정돼 있고 공통 기반이 끝났다면 **모듈 병렬**(모듈당 에이전트 1개)도 가능하다. 이때는 범위 소유권 규칙이 필수다.

### 에이전트 지시

`templates/module_brief.md`를 채워 준다. 꼭 들어갈 것:

- 읽을 문서와 절(착수 기록, PRD 결정 ID, 명세의 해당 화면 절, impl_plan 작업 ID)
- 수정 범위(자기 모듈 폴더만), 공통 요청 보고 방식, 임시 우회 시 `// TODO(common): …` 주석
- 하지 말 것(전체 테스트·빌드 실행, 다른 모듈·공통 파일 수정, 비즈니스 규칙을 Controller에)
- 검증(`dart analyze <폴더>`, `dart format`, 그리고 아래 테스트 시점 규칙에 따른 모듈 테스트)
- 보고 형식(12줄 이내)

### 테스트 시점

- **순차 방식**(모듈 1개씩): 모듈 에이전트는 자기 모듈 테스트(`flutter test test/features/<module>`)까지 돌려 보고한다. 오케스트레이터는 모듈 승인 전에 전체 `flutter test`·`dart analyze`를 한 번 돌린다.
- **병렬 웨이브**(모듈 여러 개 동시): 에이전트는 `dart analyze <폴더>`만. 테스트·빌드는 웨이브가 끝난 뒤 7단계에서 한 번에. 여러 프로세스가 같은 `build/`를 쓰면 툴이 깨지고, 공통 요청이 반영되기 전 테스트 결과는 의미가 없다.

### 리뷰와 승인

1. 모듈 완료 → 오케스트레이터가 공통 요청을 반영하고 `logs/impl_log.md`에 "완료 보고 rK"(작업 ID, 산출물, 검증 결과, 편차)를 쓴다.
2. 리뷰어(`templates/review_brief.md`)가 코드와 명세·PRD를 직접 대조해 `승인 (rK)` 또는 `수정 요청`(파일:행, 위반한 규약·결정, 기대 동작)을 로그에 추가.
3. 수정 요청이면 해당 에이전트에 피드백 → rK+1로 다시. 같은 리비전에 양측 승인이면 다음 모듈.
4. 리뷰어 판정 우선순위: 기존 사용자 차단 → 결정 준수 → 아키텍처 규약 → 작업 행 충족 → 보안(비밀값·민감 로그) → 편차는 "규약을 지키면서 더 안전한가"로 판단.

### 공통 판정

여러 모듈에 걸친 명세 해석 문제는 오케스트레이터가 `C-번호` 공통 규칙으로 판정해 로그에 남기고 전 모듈에 적용한다. 명세 자체가 모순이면 명세를 고친다(리비전 상승).

### 변형 경로 — 이미 구현된 앱에 디자인 명세를 사후 적용할 때

기본 경로는 명세 → 구현이다. 하지만 기능 구현이 끝난 Flutter 앱이 이미 있고 "UI를 원본과 똑같이 맞춰 달라"는 요청으로 들어오면(또는 3단계를 건너뛰고 구현했다면) 이 순서로 한다.

1. **3단계 명세 작성.** 기존 Flutter 구현은 근거로 쓰지 않는다. 원본만 근거로.
2. **0웨이브 — 공통 기반 갱신**: 명세 1~4장(토큰·컴포넌트·에셋·문자열), 라우트 전환, 글자 배율. 공통 파일은 이 웨이브에서만 고친다. 옛 문자열 키 → 명세 키 변환표를 만든다.
3. **1웨이브 — 모듈별 UI 리팩토링(병렬)**: 모듈당 에이전트 1개, `presentation/`만 수정(`module_brief.md`의 UI 리팩토링 선택지). 옛 공용 위젯을 새 컴포넌트로 교체. 리뷰어가 화면별로 대조해 승인.
4. **기능 계층 보류 항목**: UI 작업 중 domain·data 변경이 필요한 항목은 번호를 붙여 로그에 모은다(직접 고치지 않음). 임시 우회는 presentation 안에 `// TODO(common)`과 함께.
5. 공통 요청을 오케스트레이터가 일괄 반영.
6. **기능 수정 웨이브**: 보류 항목을 사용자에게 추천안과 함께 보여 결정을 받은 뒤 `templates/fix_briefs.md` A절로 처리. 임시 우회는 수정 후 제거해 판정 지점을 한 곳으로.
7. **7단계 통합 테스트·수정**(`fix_briefs.md` B절).

## 7단계 — 통합 테스트·수정

1. 모든 모듈(또는 웨이브)이 끝나면 오케스트레이터가 `flutter test` 전체, `dart analyze`, 빌드(대상 플랫폼별: APK, `flutter build ios --no-codesign`)를 한 번에 실행.
2. 결과를 분류: 컴파일 실패 / 실행 실패 / 커버리지 미달. 사용자에게 요약 보고.
3. 테스트 폴더별로 에이전트를 나눠 수정(`templates/fix_briefs.md` B절). 핵심 원칙: **테스트를 코드에 억지로 맞추지 않는다.** 코드가 명세·PRD와 다르면 테스트가 아니라 코드를 고친다(결함 수정으로 따로 보고). 재전송 금지·결과 미확정 같은 안전 테스트는 지우지 않는다. 공유 테스트 헬퍼는 한 담당만 고친다.
4. 커버리지 게이트: 도메인 usecase·validator 라인 100%를 권장(`tool/coverage_gate.dart` 같은 스크립트로 CI에서 강제). 쓰이지 않는 함수는 게이트를 깨므로 지운다.
5. 시간에 의존하는 테스트는 고정 시계(`now` 주입)를 쓴다. "오늘 정오" 같은 픽스처는 오후에 실패한다.
6. 다시 전체 실행해 0 실패를 확인하고 로그에 숫자(통과 수, 커버리지)를 남긴다.
