# 공동 작성·리뷰·교대 규칙

문서·코드를 두 주체(작성자, 리뷰어)가 합의해 확정하는 규칙. 리뷰어가 Fable 서브에이전트든, 사용자가 메시지를 전달하는 외부 모델이든 같다.

## 1. 공동 작성 합의 (PRD·지시서·명세)

- 본문은 작성자만 고친다. 본문은 `<!-- DOC-START rN -->` … `<!-- DOC-END rN -->` 블록에 둔다.
- 대화는 로그 파일(`logs/<문서>_log.md`)에 **추가만** 한다. 파일 전체를 덮어쓰지 않는다. 수정 직전에 최신본을 다시 읽는다(상대가 그 사이 추가했을 수 있다).
- 제목 형식: `### <이름> <번호>` — 작성자 `C-001`, 리뷰어 `G-001`처럼 주체별 번호. 단계가 있으면 `### <이름> <단계>-r<k> <내용>`.
- 각 피드백에 `동의 / 부분 동의 / 반론(근거)`으로 답한다. 근거는 원본 `파일:행`. 합의되면 본문에 반영하고 리비전을 올린다.
- 각자 **자기 이름으로만** 완료·승인을 선언한다. 상대 것을 대신 쓰지 않는다. 완료 선언 뒤 본문이 바뀌면 선언은 무효이고 새 리비전에 다시 선언한다.
- 미해결 피드백은 지우지 않는다.
- 상단에 상태 표: `| 참여자 | 역할 | 최종 합의 (리비전) |`.
- 확정 후 사용자가 원하면 대화 로그를 정리하고 본문만 남긴다.

## 2. 구현 리뷰 (모듈 단위)

- 로그: `logs/impl_log.md`. 맨 위 진행 상태 표, 아래 로그.
- 작성자: `### <작성자> M<n>-r<k> 완료 보고` — 작업 ID, 산출물 경로, 검증 결과(analyze/test/build), 편차·미결.
- 리뷰어: `### <리뷰어> M<n>-r<k> 검토 — 승인 (r<k>)` 또는 `— 수정 요청`. 수정 요청은 항목마다 `파일:행`, 위반한 규약·결정 ID, 기대 동작.
- 리뷰어는 진행 상태 표의 자기 셀만 바꾼다.
- 리뷰어는 코드를 쓰지 않는다.

## 3. Fable 서브에이전트로 리뷰할 때

- `Agent` 호출에 `model: "fable"`. 프롬프트는 `templates/review_brief.md`를 채운다. 작성자의 보고 대신 산출물 경로와 기준 문서 경로를 준다.
- 결과를 구조화하려면 판정·이슈 목록 형식을 지정한다(`verdict: approve|needs_fix`, `issues: [{severity, location, problem, evidence, fix}]`).
- 지적을 받으면 오케스트레이터가 원본·코드로 재확인한 뒤 반영 또는 반려(근거 기록). 리뷰어 지적도 틀릴 수 있다.
- 수정 후 같은 리뷰어 관점으로 재검토해 `approve`가 나올 때까지 반복한다. 3회 넘게 같은 쟁점이 돌면 사용자에게 판단을 요청한다.

## 4. 외부 모델과 일할 때

- 외부 모델은 이 세션의 파일을 직접 못 볼 수 있다. 사용자가 전달한다. 전달할 **짧은 안내문**(무엇을 읽고, 어디에 어떤 형식으로 쓰는지)을 만들어 사용자에게 준다.
- 외부 모델이 같은 원본을 독립 분석하게 하면(예: UI 인벤토리) 서로 놓친 것을 잡는다. 그 산출물은 `docs/<단계>/<모델명>/`에 둔다.
- 사용자가 "전달했어"라고 하면 로그 파일을 다시 읽어 상대 기록을 확인하고 이어 간다. 상대 기록이 아직 없으면 기다린다고 말한다.

## 5. 리뷰어 교대

사용량 소진 등으로 리뷰어가 바뀔 수 있다. `REVIEWER_HANDOVER.md`를 만들어 둔다:

1. 지금 무슨 일을 하는가(한 문단)
2. 문서 경로와 역할 표
3. 리뷰 절차(어디서 대기 항목을 찾고, 어디에 어떤 제목으로 쓰는지)
4. 검토 기준(우선순위 순)
5. 현재 상태
6. 교대 기록 표(기간 / 리뷰어 / 비고)

교대 시 로그 상단 규칙 블록에 한 줄을 추가하고, 이전 리뷰어의 승인은 유효하다고 적는다.
