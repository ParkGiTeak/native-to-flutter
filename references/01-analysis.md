# 1단계 — 원본 분석

목표: 원본 앱을 "Flutter로 다시 만들 수 있을 만큼" 문서화한다. 이 단계 산출물이 이후 모든 문서의 근거 출처다. 여기서 놓친 동작은 실기기 QA에서 사용자가 발견하게 된다.

## 1. 에이전트 구성

| 모드 | 에이전트 |
|---|---|
| BOTH | iOS 분석 1개 + Android 분석 1개를 병렬로. 둘 다 끝나면 대조 에이전트 1개(또는 오케스트레이터)가 차이 목록을 만든다 |
| 단일 OS | 원본 OS 분석 1개. 원본이 크면 기능 영역별로 나눠 2~3개 |

각 분석 에이전트에게 `templates/analysis_brief.md`를 준다. 원본 경로, 산출물 경로, 아래 목차, 근거 규칙을 채워 넣는다.

## 2. OS별 분석서 `analysis/<os>_analysis.md` 목차

1. **개요**: 분석 기준 스냅샷(경로, 버전·빌드 번호, git 커밋 또는 "git 없음", 스토어 배포본과의 일치 여부 — 확인 못 했으면 "미검증"), 버전, 최소 OS, 빌드 구성·환경, 서버 base URL별 환경, 주요 의존성(이름·버전·용도)
2. **구조**: 폴더 구조, 화면 진입점, 네비게이션 방식(스토리보드·코디네이터·Activity/Fragment·Navigation), 공통 베이스 클래스
3. **화면 목록**: 화면마다 `ID(임시) / 클래스 / 진입 경로 / 나가는 경로 / 로그인 필요 / 주요 동작`. **도달할 수 없는 화면**(코드는 있지만 진입 UI가 숨겨짐)도 표시한다 — 구현 범위에서 빼는 근거가 된다
4. **API**: 엔드포인트마다 `메서드 / 경로 / 요청(쿼리·바디·헤더) / 응답 필드 / 호출 화면 / 성공 판정(상태코드) / 오류 처리`. 인증 헤더, 토큰 갱신, 타임아웃, 재시도, 암호화(필드 단위 암호화가 있으면 알고리즘·키 위치·IV·패딩)
5. **비즈니스 규칙**: 입력 검증(정규식·길이), 금액·시간 계산, 상태 판정, 정렬·필터, 페이징 파라미터, 시간대 처리
6. **세션·저장**: 토큰 저장 위치, 로그아웃·탈퇴·만료 시 지우는 것, 로컬 저장 키 전부(이관 대상)
7. **플랫폼 연동**: 권한(언제 요청, 거부 시 동작), 푸시(payload 키, 토픽, 포그라운드·백그라운드·종료 상태 탭 처리), 딥링크·스킴, 웹뷰 JS 브리지, 카메라·QR·OCR, 지도, 결제·본인인증 SDK, 보안 검사(루팅·탈옥·디버거·변조), 분석·크래시
8. **알려진 결함**: 코드에서 보이는 버그·경쟁 상태·무한 대기·누락된 처리. 각 항목에 근거와 사용자 영향
9. **비밀값 노출**: 소스에 들어 있는 키·시크릿 목록(값은 적지 않고 위치만)

## 3. 공통 산출물

- `analysis/api_inventory.md`: 모든 API를 하나의 표로. BOTH면 OS별 사용 여부·차이 열을 둔다. ID(`API-01`…)를 붙인다
- `analysis/screen_inventory.md`: 화면 ID(`S01`…)를 확정한다. BOTH면 두 앱의 대응 화면을 한 행에 묶는다. 이 ID를 이후 모든 문서가 쓴다
- (BOTH) `analysis/business_diff.md`: 같은 기능이 OS별로 다르게 동작하는 곳 전부. 형식은 아래

```markdown
| ID | 항목 | iOS 현재 (근거) | Android 현재 (근거) | 사용자 영향 | 권장 결정 | 서버 확인 필요 |
```

우선순위를 붙인다: P0 = 돈·주문·인증·보안·푸시 도달, P1 = 주요 기능 일관성, P2 = 표시·문구.

## 4. 모드별

- **BOTH**: 차이를 찾을 때 "한쪽이 버그"인 경우가 많다. 그때 권장 결정은 "올바른 쪽 동작"이지 "기준 OS 동작"이 아니다(기준 OS는 UI에만 적용). 두 앱 모두 운영 중이고 같은 서버를 쓰므로, 한쪽만 보내는 파라미터·한쪽만 쓰는 API 버전은 양쪽 다 서버가 받아 준다는 뜻이다. 통합할 때 그 사실을 근거로 쓴다.
- **단일 OS**: 차이 목록 대신 `analysis/new_platform_gaps.md`를 만든다(새로 지원할 OS가 있을 때). 원본 OS에는 없지만 새 OS에서 반드시 정해야 하는 것: 뒤로가기(Android 하드웨어·제스처 / iOS 엣지 스와이프), 권한 모델·문구, 알림 권한·채널, 시스템 바·노치·safe area, 앱 ID·서명·스토어 등록, 푸시 설정(APNs 키 / FCM), 원본 SDK의 새 OS 지원 여부와 대체안.

## 5. 리뷰

리뷰어(`templates/review_brief.md`, 대상: 분석서)는 무작위로 화면·API를 골라 원본 파일을 직접 열어 근거가 맞는지 확인하고, 빠진 화면·API·저장 키를 찾는다. 지적은 분석 에이전트에게 돌려 반영시킨다. 승인되면 2단계로 간다.

## 6. 흔한 누락

- 앱 시작 시퀀스(버전 검사, 강제 업데이트, 점검 공지, 자동 로그인, 이관)
- 서버 메시지 문자열 비교로 분기하는 코드(예: 특정 한글 메시지면 세션 정리)
- 화면 복귀 시 재조회(`viewWillAppear`/`onResume`) — Flutter로 옮길 때 자주 빠진다
- 로그인 전후 홈 상태 갱신
- 같은 기능의 진입 경로가 여러 개일 때 경로별 차이
- 앱 종료 상태에서 푸시를 눌렀을 때의 흐름
